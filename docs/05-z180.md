## Processor and clock

- Zilog Z8S18020VSC (20 MHz grade) on s20/s108/s109; [s128](sources.md#s128) has Z8S18016VSC (16 MHz grade). Both are Z8S180, PLCC-68.
- EXTAL comes from a 36.000 MHz oscillator. After reset the Z8S180 divides its input by 2,
  and the firmware never writes the clock registers CMR ($1E) or CCR ($1F). So the CPU
  runs at **18 MHz**. This exceeds the 16 MHz grade fitted on s128; the scan does not
  establish timing compliance. Source: [Z8S180 specification](sources.md#s62).
- The [prototype drawing](sources.md#s26) fed EXTAL from the 40 MHz OTI-068 memory clock through R38, which
  gives the "20 MHz" in Sequential's papers. Production does not fit R38.
- The firmware turns DRAM refresh off (RCR = 0): the card only has static RAM on the Z180
  bus. Source: [`ROM_BEEF.asm`](sources.md#s27) reset.

## Physical memory map

The Z180 has a 20-bit (1 MB) physical address space. GALs U15 (memory decode) and U4 (I/O
decode) select its memory and I/O devices. Where the SRAM, the EPROM, their mirrors, the
video-half controls and the VGA window sit: [physical memory map](reference/z180-memory-map.md#memory-map);
what each access does: [region details](reference/z180-memory-map.md#region-facts-and-evidence).

### How the SRAM is used

The 128 KB SRAM is two 64 KB banks that mirror the Apple's main and auxiliary memory.
The Apple-side copy ([Capture logic](04-capture-logic.md)) writes each caught byte to
`bank * $10000 + Apple address`. The firmware lives in bank 0, outside the screen copies;
one case of the original Lattice chip's bank rule copies over it
([E28](reference/errata.md#e28-with-80store-on-u7-picks-the-copys-bank-without-looking-at-the-address)).

Which SRAM holds the screen copies, the firmware and the command buffers:
[SRAM ownership map](reference/z180-memory-map.md#sram-ownership). Super Hi-Res ($2000-$9FFF)
and the auxiliary hires pages ($2000-$5FFF) share bank 1. SRAM contents survive a card reset.

### MMU

The firmware's normal setting is CBAR = $F2, BBR = 0, CBR = 0: logical = physical for
$0000-$FFFF, which is SRAM bank 0. Renderers and commands reprogram BBR/CBR to reach bank 1
($10000), the EPROM, the switch areas and the VGA window, and restore them afterwards.
RunCode lets the host set CBR, CBAR and BBR for its own code. The manual requires
CBAR's low nibble to remain 2, keeping handlers at $0000-$1FFF. Source: [Firmware documentation](sources.md#s15) pp9-10.

## Boot

On reset the Z8S180's ASCI control register CNTLA0 has bit 4 set, so its /RTS0 pin is high.
GAL U15 has /RTS0 as an input and maps the **EPROM at $00000** while it is high. Source: schematic U15 pins.

```
reset (Apple /RESET via U17)
  -> Z180 starts at $0000 = EPROM: jp $0080
  -> di; port $AD = 0; port $A1 = $08 (MODE_D3 on, copying on); read port $AA
  -> MMU: CBAR $F0, CBR $21; SP = $F0FF (physical $300FF, the SRAM mirror)
  -> refresh off; INT0-2, timers, DMA, CSI/O, ASCI interrupts off
  -> write $01 to $01FD and read it back
       EPROM still mapped: reads 0 -> DMA-copy EPROM $0000-$03FF, $0C00-$1FFF, $6000-$FFFF
                                    to physical $2xxxx (= SRAM bank 0), then clear CNTLA0
                                    bit 4: /RTS0 low, SRAM at $00000
       RAM already mapped (a jump to $0000 from RunCode): reads 1 -> skip the copy
  -> DCNTL = 0; SP = $03FF; enable OTI-087X add-on mode; I register; softswitch table
  -> enable INT1; port $A0 = 0 (handshake idle); MMU CBAR $F2, BBR 0, CBR 0; ei
  -> main loop at $1E01
```

([`ROM_BEEF.asm:54-227`](sources.md#s27))

On a cold boot the $01FD probe writes against the EPROM for one cycle, and the read returns
the EPROM byte $00 ([EPROM write contention](reference/z180-memory-map.md#eprom-write-contention)).
Source: [netlist](../data/netlist/README.md) U10/U15.

- The softswitch setup ([`ROM_BEEF.asm:2535-2560`](sources.md#s27)) starts with: text on, 80STORE off,
  Super Hi-Res off, emulation on, and a mode change pending. So the first main-loop pass
  selects **Apple 40-column text** and the card shows whatever is in its SRAM copy of text
  page 1.
- A routine at $0208 would set a 640x480x256 (VGA) or 640x400x256 (RGB) mode, draw a
  boot picture from the EPROM's upper 64 KB and keep an $A5 signature at physical $3FFFF.
  **Nothing calls it**: the ROM holds no call, jump or pointer to $0208, and the EPROM's
  upper half is all zero. It is unfinished code.

## Interrupts

The Z180 vectors INT1 and INT2 through its I register. ROM 1.4 enables only INT1
(ITC bit 1); its handler dispatches Apple events and commands
([event handler](08-firmware.md#the-event-handler-int1),
[vector addresses](reference/z180-memory-map.md#interrupt-vectors)).
Source: [ROM_BEEF.asm:593-625](sources.md#s27).

RST $38 writes `*` to the ASCI0 transmitter. NMI runs through zero bytes into the reset
code. Neither occurs during normal firmware operation.

## DMA

The firmware uses both DMA channels ([firmware DMA channels](reference/z180-io-ports.md#firmware-dma-channels)).
Channel 1 turns each Apple event into one transfer through port $A0; that transfer
acknowledges the event, which allows the next DREQ1 edge. The
[command sequence](09-host-protocol.md#one-command-step-by-step) shows it with the
back-to-back 16-bit stores of [`VGALOW.ASM WritePage`](sources.md#s29).

## Wait states

DCNTL sets automatic waits, and the external /WAIT input can stretch an access further.
Sources: [Zilog UM0050](sources.md#s39); schematic U15.

### Automatic waits

The firmware writes DCNTL = 0 after the boot copy: no automatic memory waits and one
external-I/O wait ([automatic wait counts](reference/clocks.md#z180-automatic-waits)).
SHR setup writes zero again. Later DMA setup changes the low control bits while
preserving the automatic-wait fields. These instructions do not program U15's wait
count. Sources: `firmware/v1.4/src/boot.asm`, `start_firmware`; `superhires.asm`,
SHR setup; `commands.asm`, `dma_upload`; [Zilog UM0050](sources.md#s39), DCNTL tables 3 and 4.

### External waits and worst-case margins

U15 drives /WAIT from the OTI-087X's IOCHRDY (pin 79, pulled up by R32) and its own address
decode. The Z180 samples /WAIT at the falling edge of T2 and of every wait state, 55.6 ns
apart. Its automatic waits (DCNTL) and /WAIT overlap, and the cycle ends when both allow
it (UM0050 pp27-28). Times in this section are measured from the rising edge of T1.

Three separate limits set how long a video memory access lasts. They overlap: the access
ends at the first /WAIT sample at which all three allow it, so their counts do not add.

1. **The Oak's bus timing minimum.** The Oak needs its memory command at least 165 ns
   wide (OTI-087 p47). At 18 MHz that takes at least 2 waits for a read and 3 for a write
   at worst case ([VGA bus timing](reference/clocks.md#vga-bus-timing)). This is a floor
   on the count, not the count.
2. **U15's forced waits.** IOCHRDY can go low as late as about 93 ns: the command starts
   about 63 ns after T1 rises, and the Oak may take 30 ns more (p47). That is after the
   first /WAIT sample deadline, near 68 ns, so U15 must start the first wait from its own
   address decode. U15 has no /RD or /WR input, so it forces the same count on reads and
   writes. The count is not recovered; a design that meets the worst-case write forces at
   least 3 ([U15](07-glue-logic.md#u15-memory-decode-boot-overlay-half-switch-waits)).
3. **The Oak's IOCHRDY.** The Oak holds IOCHRDY low until its DRAM has served the access
   ([how long IOCHRDY holds an access](#how-long-iochrdy-holds-an-access)). A read the
   read cache does not hold takes about 4 waits even with the DRAM idle, and more behind
   a display fetch or refresh.

The AT bus, which the OTI-087X is built for, allows IOCHRDY low for at most 2.5 us, about
45 Z180 clocks. That is a rule for card designers, not a limit inside the Oak. Source:
[IBM PC AT Technical Reference](sources.md#s77), "I/O CH RDY".

### How long IOCHRDY holds an access

The Oak holds IOCHRDY low until it has finished a CPU memory access. A read the read
cache already holds, and a write the write cache takes, finish without a DRAM cycle
(databook p5). Every other access waits for the Oak's DRAM, which it shares with display
fetch and refresh. Ext $20 bits 3-0 set how full the display FIFO must be before the Oak
processes a CPU read or write; bits 7-4 are reserved and the default is 1 (p41). ROM 1.4
sets 1 or 5, depending on the mode ([video modes](reference/video-modes.md)). The
databook says the write cache "must not be enabled for AT-bus implementations" (p42), yet
its AT-bus overview describes zero-wait writes through that cache (p5), and ROM 1.4 sets
it in most mode records ([write cache](reference/oti087-registers.md#write-cache)). The
emulators honor the bit.

At the card's 40 MHz MCLK one memory clock is 25 ns. The databook's DRAM minimums are a
7-clock random read or write cycle (175 ns), a 3-clock RAS precharge, a 4-clock RAS pulse
and a 2-clock page-mode cycle; read data arrives at most 4 clocks after RAS (p56).
Refresh uses CAS-before-RAS cycles, 3 or 5 per scan line (CRTC $11 bit 6), or 1 when
ext $21 bit 7 is set (p41). ROM 1.4 uses 3 in its VGA modes and 5 in most RGB modes. Oak's
earlier [OTI-037 data sheet](sources.md#s133) gives the same 3/5 rule (p2-12) and draws a
RAS precharge each time the DRAM passes between the display and the CPU (p2-24).

No Oak document gives the display FIFO's size, the order in which refresh, display fetch
and the CPU are served, how many memory clocks the Oak takes to accept a CPU request, the
cache sizes, or a longest IOCHRDY time. The AT bus's 2.5 us IOCHRDY limit is a rule for
card designers, not a limit inside the Oak. Sources: [OTI-087 databook](sources.md#s02)
pp4-5, 41-42, 47, 56.

**When the Oak lets go.** The Oak's MCLK and the Z180's clock come from separate crystals
([clocks](reference/clocks.md)), so a CPU request reaches the Oak at an arbitrary point in
a memory clock. If the Oak accepts the request on the second MCLK edge after it arrives
(25 to 50 ns later; no document gives this) and then runs at the p56 minimums, it releases
IOCHRDY this long after the command reaches it:

| What the DRAM is doing when the access arrives | Read | Write, cache off or full |
|---|---|---|
| Idle, FIFO at its ext $20 level | 150-175 ns | 200-225 ns |
| Only the last display fetch's 3-clock precharge left | 225-250 ns | 275-300 ns |
| One whole display fetch still to run | 325-350 ns | 375-400 ns |
| 3 refresh cycles still to run, back to back | 700-725 ns | 750-775 ns |
| 5 refresh cycles still to run, back to back | 1050-1075 ns | 1100-1125 ns |

These are the shortest times the documented minimums allow; the real chip may take more
memory clocks. The databook does not say whether a line's refresh cycles run back to back;
the card's copy timing shows a waiting access is not held behind all of them
([copy timing budget](07-glue-logic.md#copy-timing-budget)).

**From release to Z180 waits.** After the Oak lets go, R32 pulls IOCHRDY up, U15 passes it
to /WAIT, and the Z180 samples /WAIT at each falling clock edge, 55.6 ns apart. /WAIT must
be steady 15 ns before the edge ([UM0050](sources.md#s39) Table 31, tWS). The access ends
at the first sample that finds /WAIT high, once U15's own forced waits are also done. The
two run at the same time, so their counts do not add.

IOCHRDY is an open-drain output (databook p19), so only R32 raises the line. The net has
three parts on it: the Oak's pin 79 (at most 8 pF, databook p57), U15's input (at most 6 pF,
[AMI data sheet](sources.md#s131) p19) and R32, plus the trace
([netlist](../data/netlist/README.md)). Reaching U15's 2.0 V input-high level (AMI p19)
takes about 0.5 x R32 x C: 1 ns per pF at 2.0 kohm and 5 ns per pF at 10 kohm. The two
pins' 14 pF alone give about 14 ns at 2.0 kohm and 70 ns at 10 kohm; no source gives the
trace's share. U15's delay is 10 ns for a -10 part and 15 ns for a -15 part (AMI p20), if
its /WAIT output is combinational; its equations are not recovered.

R32 is 2.0 kohm (`202`) on [s20](sources.md#s20) and [s108](sources.md#s108), but
10 kohm (`103`) on the production [s109 card](sources.md#s109). The
[s128](sources.md#s128) R32 is fitted, but its value cannot be read.

Example, a read from idle DRAM, timed from the rising edge of T1 as above. The command
reaches the Oak at about 63 ns (T1's falling edge at 27.8 ns, the Z180's /RD delay, then
the ACT32 gate), and the Oak releases IOCHRDY at about 213-238 ns. The samples that end
the access after 3, 4, 5 and 6 waits fall at 250, 306, 361 and 417 ns, and /WAIT must be
high 15 ns before each. With 2.0 kohm, the 14 pF of pins and a -10 U15, /WAIT goes high at
237-262 ns, 29-54 ns before the 306 ns sample needs it: 4 waits. About 29-54 pF of trace,
or one more memory clock in the Oak, moves it to 5. With 10 kohm the same read is ready at
293-318 ns: 5 waits, or 6 with about 6-11 pF or more of trace. An uncached write from idle
DRAM releases 50 ns later: 5 waits at 2.0 kohm, 4 only when the Oak takes it at its
earliest.

The existing 18 MHz calculation uses the 100 ns Toshiba SRAM and its assumed U15
decode delay: read and opcode-fetch margins are short by 16 and 44 ns. Keep those
assumptions with the result; the PLD grades vary by card. The s128 NEC SRAM is marked
-70L (70 ns), with ES also printed, and that card uses ICT -15 PLDs and a 16 MHz CPU
grade. The Toshiba calculation is not a timing guarantee for s128. Sources:
[PLD markings](02-board.md#pld-markings), [s128 scan](sources.md#s128),
[PS0140](sources.md#s62) Table 8; [Toshiba SRAM databook](../data/netlist/SOURCES.md#package-pinouts-used) B-38.

### A functional timing estimate

[Second.Sight.Info.txt](sources.md#s40) gives eight 20 MHz clocks per copied byte for
the blitter. Jawaid Bazyar's [May 8, 1995 announcement](sources.md#s130)
gives six for the same question. Six is the Z180's base DMA byte time: a three-clock
read and a three-clock write before waits. Neither statement specifies source,
destination, video mode or measurement conditions. They do not identify U15's forced
wait count or U17's shadow-copy timing.

An emulator gets each access's waits from the Oak's DRAM timeline and the steps above.
One that charges fixed waits instead uses these counts. They cover an access that meets
no display fetch or refresh, with R32 at 2.0 kohm as on the s20 and s108 cards:

| Access | Z180 waits |
|---|---|
| Video memory write, write cache on (ext $22 bit 3) | 3 |
| Video memory write, write cache off | 5 |
| Video memory read | 5 |
| VGA register I/O | 1 |

Three is the count that meets the Oak's worst-case write timing; U15 cannot tell reads from
writes, so reads get it too. Five is the top of the idle read and uncached write in the
example above. The 10 kohm card adds one or two. A fixed count cannot cover contention:
a read that arrives behind a display fetch or a refresh cycle waits longer.

The write cache lets a write end at once "unless the cache is full" (p5). Back-to-back Z180
video writes are at least one 3-wait write cycle apart, 6 clocks (333 ns), longer than the
Oak's 200-225 ns idle write, so the Z180's writes alone never fill the cache; a refresh or
display fetch in progress can. A read the read cache already holds also ends at once (p4),
so it takes only U15's 3. The databook says only that a read next to the one before it in
a block move often hits (p5); no Oak document gives which addresses the cache holds, its
size, or what empties it. A fixed-wait emulator therefore counts every video memory read
as 5.

What those waits mean for the Apple-side copies:
[copy budget](07-glue-logic.md#copy-timing-budget).

## The card's I/O ports

The Z180 uses 16-bit I/O addresses (`out (c)` puts B on A8-A15). Its internal registers
sit at $00-$3F; U4 decodes the rest from HA0-HA7 and the I/O strobe
([port table](reference/z180-io-ports.md#port-table)). Card ports repeat every 256 I/O
addresses; VGA ports use the full address. ROM 1.4 never uses $A2, $A3, $AC, $AE or $AF.
Source: [netlist](../data/netlist/README.md).

## Other on-chip features

- **ASCI0:** the softswitch handlers write single trace characters (`F`, `N`, `M`, ...) to
  its transmit register. The drawing connects TXA0 to
  nothing ([connections the drawing leaves out](reference/board-connections.md#connections-the-drawing-leaves-out)).
- **CSI/O, timers, ASCI1:** turned off at reset and never used by ROM 1.4. Source:
  [Zilog UM0050](sources.md#s39).
- **CTS1:** the library source says the card can poll "the CTS1 pin" for data in one
  transfer mode ([VGALOW.ASM](sources.md#s29)). The 1.4 firmware never reads it.

## What ROM 1.4 needs from the processor

What a Z180 soft core must have to run the unchanged ROM, from the
[firmware source](../firmware/README.md). Custom code uses the rest of the chip too
([Beyond the firmware](14-custom-code.md)).

- **Instructions beyond the Z80 set:** `IN0`, `OUT0` and `MLT` (on BC and DE) only. The
  ROM never uses `TST`, `TSTIO`, `OTIM`, `OTIMR`, `OTDM`, `OTDMR` or `SLP`. Every `OUT0` of
  A follows an `LD A,A`, a habit of the source, not a requirement.
- **Interrupts:** INT1 only, vectored through I = $0C with IL left at 0, so its vector is
  the word at $0C00 ([vector addresses](reference/z180-memory-map.md#interrupt-vectors)).
  The ROM never executes `IM`, so INT0 stays in mode 0 and disabled. The INT1 handler
  ends with `EI` and `RET`; the one `RETI` is in unreached code.
- **Internal registers**, all reached with `IN0`/`OUT0`:
  - At boot, read-modify-write: ITC (INT0-INT2 off), TCR (both timer interrupts off),
    DSTAT (both DMA interrupts off), CNTR (CSI/O interrupt off), STAT0 and STAT1 (both
    transmit interrupts off), and RCR = 0 (refresh off). ITC later turns INT1 on.
  - ASCI0: CNTLA0 bit 4 (/RTS0, which switches the [boot overlay](#boot)) and TDR0 (trace
    characters).
  - DMA channel 0: SAR0, DAR0, BCR0 (memory to memory, including fills from a fixed
    source). DMA channel 1: MAR1, IAR1, BCR1 (port $A0 to and from memory, one byte per
    DREQ1 edge). Both: DSTAT, DMODE, DCNTL. Modes and handshake:
    [firmware DMA channels](reference/z180-io-ports.md#firmware-dma-channels), [DMA](#dma).
  - MMU: CBR, BBR, CBAR ([MMU](#mmu)).
- **Never touched:** IL, OMCR, the Z8S180 clock registers (the chip stays at its reset
  divide of 2: [Processor and clock](#processor-and-clock)), the timer counters and reload
  registers, ASCI1 data and the CSI/O data register.
- **Timing:** the waits that matter are handshakes with the Apple side and polls of the
  Oak's retrace status. One pause counts instructions: `delay_loop` ($0EAE) runs 32,767
  passes of 26 clocks, about 47 ms at 18 MHz, between the sequencer restart and the CRTC
  writes of every mode change, just after the new pixel clock is selected. A faster core
  shortens that pause.
